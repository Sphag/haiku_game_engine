# Build

The project configures and builds offline. Configuration never downloads anything:
third-party sources live in `third_party/` and are checked against
`third_party/manifest.json` by `cmake/ValidateVendor.cmake`.

## Tools

| Tool | Verified version | Notes |
|---|---|---|
| CMake | 3.31.6 (Linux), 4.3.4 (Windows) | Requires 3.28 or newer. |
| Ninja | system install | Used by the `Ninja Multi-Config` generator. |
| MSVC | 14.38.33130 (VS 2022 Community) | Run configure from an x64 developer environment (`vcvars64.bat`). |
| Clang | 10.0.0 with libstdc++ 9 | Linux default compiler (`linux-dev`, `linux-asan`). |
| GCC | 9.4.0 | Linux GCC preset (`linux-gcc`). |

The Linux compilers above are the versions installed on the verification machine
(Ubuntu 20.04 under WSL2). GCC 9 and libstdc++ 9 do not provide `<span>` and other
newer C++20 library headers, so first-party code avoids them. CI (US-004) should pin
newer compilers and record the versions it uses here.

## Presets

Configure with `cmake --preset <name>`; build with `cmake --build --preset <name>`;
test with `ctest --preset <name>`. Each configure preset writes to `build/<preset>`.

|---|---|---|
| `win-dev` | Windows | MSVC (environment from `vcvars64.bat`) |
| `linux-dev` | Linux | Clang |
| `linux-gcc` | Linux | GCC |
| `linux-asan` | Linux | Clang, AddressSanitizer + UndefinedBehaviorSanitizer |

## Quality gates

```sh
cmake -P cmake/ValidateVendor.cmake
cmake --preset linux-dev
cmake --build --preset linux-debug
ctest --preset linux-unit --output-on-failure --no-tests=error
```

On Windows, run the same sequence from an x64 developer environment with `win-dev`,
`win-debug`, and `win-unit`.

First-party targets compile with warnings treated as errors (`-Wall -Wextra -Wpedantic
-Wshadow -Werror`, or `/W4 /WX` on MSVC). Vendored Catch2 keeps its own flags.

## Shader toolchain

The pinned DirectXShaderCompiler (`third_party/dxc`) is built from source on every configure/build preset.
It is a separate CMake project (`ExternalProject_Add(engine_dxc_host)` in `cmake/ShaderToolchain.cmake`):
its compiler flags, language level, and warnings are its own, so engine flags such as `-Werror` and `/WX`
are never forwarded. The host compilers are passed in explicitly from the parent project's `CMAKE_C_COMPILER`
and `CMAKE_CXX_COMPILER`.

Outputs are staged under `build/<preset>/tools/shader-toolchain/`:

| Platform | Compiler | Validator and runtime | License notices |
|---|---|---|---|
| Linux | `bin/dxc` (RUNPATH `$ORIGIN/../lib`) | `lib/libdxcompiler.so`, `lib/libdxil.so` | `licenses/` |
| Windows | `bin/dxc.exe` | `bin/dxcompiler.dll`, `bin/dxil.dll` | `licenses/` |

`dxil` is the DXIL validator. Without it dxc cannot sign DXIL. The staging step
(`cmake/InstallShaderToolchain.cmake`) fails if any of these files is missing.

Shaders are compiled only with this staged binary (`ENGINE_DXC_EXECUTABLE`); `dxc` is never looked up on `PATH`.
`engine_add_hlsl_shader(<name> SOURCE <file> ENTRY <fn> PROFILE <target>)` writes `build/<preset>/shaders/<name>.dxil`
and `<name>.spv` as part of the default build. `tests/shaders/fixture.hlsl` is the fixture; the CTest
`engine_shader_*` tests check the magic numbers, that the DXIL validator digest is nonzero, and that
`tests/shaders/fixture_error.hlsl` fails with `<path>:7:` and `error:` in the diagnostic.

Set `-DENGINE_BUILD_SHADER_TOOLCHAIN=OFF` to skip the DXC build and the shader tests, for example when iterating on
engine code. The default is ON, and the quality gates use the default.

### Prerequisites checked at configure time

Configure stops with a message naming the missing piece before the large DXC build starts:

- Ninja (`ninja` or `ninja-build` on PATH). The DXC sub-build always uses Ninja.
- Python 3.8 or newer. SPIRV-Tools and DXC run Python generators during the build.
- Windows: the Windows SDK (`<windows.h>`) and ATL (`<atlbase.h>`, the "C++ ATL for latest v143 build tools" component).
- Linux: glibc headers and `dlopen` (`libc6-dev`).

### Offline and build-tree rules

- The DXC configure passes `LLVM_INFERRED_HOST_TRIPLE` on Linux because the vendored tree has no
  `autoconf/config.guess`. Windows uses the MSVC branch of DXC's host detection.
- Vendored DirectX-Headers stand in for the Windows SDK's d3d12 headers on Linux (`DIRECTX_HEADER_INCLUDE_DIR`).
- DXC is configured with `HLSL_DISABLE_SOURCE_GENERATION=ON`: the generated sources it would rebuild with HCT
  are committed in the vendored tree, and the HCT docs tree is not vendored.
- `LLVM_ENABLE_EH=ON` and `LLVM_ENABLE_RTTI=ON`: DXC source uses exceptions and RTTI (the Windows HCT scripts set the same).
- The generators run with `PYTHONDONTWRITEBYTECODE=1`. Without it, Python writes `__pycache__` into `third_party/`,
  and the vendor validator rejects those files.
- The sub-build runs on every build (`BUILD_ALWAYS`). Ninja makes it incremental, so an unchanged tree is a no-op.
- The host toolchain needs no network: `DOWNLOAD_COMMAND`, `UPDATE_COMMAND`, and `PATCH_COMMAND` are empty.

## Continuous integration (US-004)

Workflows live in `.github/workflows/`. Every CPU job runs `cmake -P cmake/ValidateVendor.cmake`, configures a
preset, builds, and runs CTest with `--output-junit`, so each job uploads a JUnit XML report artifact
(`artifacts/reports/`) even when tests fail.

| Job | Runner | Gate | Report |
|---|---|---|---|
| `windows-msvc` | `windows-2022`, MSVC via `ilammy/msvc-dev-cmd` | `win-dev`, `win-debug`, `win-unit` | `win-msvc-unit.xml` |
| `linux-clang` | `ubuntu-22.04`, clang-14 | `linux-dev`, `linux-debug`, `linux-unit` | `linux-clang-unit.xml` |
| `linux-gcc` | `ubuntu-22.04`, gcc-11 | `linux-gcc`, `linux-gcc-debug`, `linux-gcc-unit` | `linux-gcc-unit.xml` |
| `linux-sanitize` | `ubuntu-22.04`, clang-14 | `linux-asan`, `linux-asan`, `linux-sanitize` (ASan + UBSan) | `linux-asan-ubsan.xml` |
| `offline-build` | `ubuntu-22.04`, clang-14 | `tools/ci/offline_verify.sh`, see below | `offline-linux-dev-unit.xml` |
| `gpu-status` | `ubuntu-22.04` | writes `not-run` records (see GPU jobs) | `gpu-*.json` |

CMake 3.31.6 and Ninja 1.11.1.3 are installed with pip, so runners do not depend on their image's versions.
GCC 11 and clang-14 are the CI compilers. The local verification machine uses GCC 9.4 and clang 10, so CI
results and local results can differ on compilers.

### Offline build verification

`tools/ci/offline_verify.sh` runs the Linux clang gate inside `unshare -rn`, a new user and network namespace
with only the loopback interface. It checks that the namespace has no interface other than `lo` and that a TCP
connection to a public address fails, then removes `build/linux-dev`, configures, builds, and runs unit tests.
Any download attempt fails the job, so a cache miss cannot fetch sources. Run it locally with
`bash tools/ci/offline_verify.sh`.

### GPU jobs

GPU jobs live in `.github/workflows/gpu.yml`, separate from CPU CI. They run only on self-hosted runners labeled
`gpu` (`windows,x64` for DX12 and Vulkan; `linux,x64` for Vulkan), and only when the repository variable
`GPU_RUNNER_ENABLED` is `true`. Hosted runners, WSL, and software rendering (WARP, llvmpipe, SwiftShader) do not
satisfy these jobs.

Each environment writes `artifacts/reports/gpu-<environment>.json` with one of these statuses:

- `passed`: the GPU suite ran and succeeded.
- `failed`: the suite ran and failed, or the binary was not built.
- `unsupported`: the runner exists, but `engine_tests` has no `--suite gpu` yet. This is the status today.
- `not-run`: no GPU runner is registered. `gpu-status` writes this for every environment.

No GPU result is recorded as `passed` until the suite exists and runs.

## Test layout

- `engine_tests` is the CPU test executable. Its `--suite` option selects `unit`,
  `integration`, or `all` (default).
- CTest labels are `unit` and `integration`. CLI contract tests (`tests/cli/CliContract.cmake`)
  run the built executable and check exit codes and messages for `--help`, unknown
  arguments, and invalid suite values.
- Exit codes: `0` success or help, `2` invalid command line, other nonzero values are
  failed-test counts.

`third_party/manifest.json` records URL, revision, archive SHA-256, license, patches,
dependency relationships (`dependsOn`), the prohibited dependency list, the system ABI
exceptions, and a SHA-256 for every vendored file. Validation fails for a missing,
modified, or unlisted file, a submodule, Git LFS, Git metadata inside `third_party/`,
a prohibited dependency, a dangling `dependsOn`, or a modified patch.

Regenerate the vendored sources and manifest with
`python3 -I tools/vendor/vendor.py --download-dir <new empty dir> [--only NAME ...]`. This is a
maintainer tool; CMake never runs it. Validate with `cmake -P cmake/ValidateVendor.cmake`,
which configure also runs. On WSL over a Windows drive, validation of the full set takes
about 1.5 minutes because every file is hashed.

### Scope decisions

- The Vulkan components use one consistent set: Vulkan-Headers, Vulkan-Loader, Vulkan-Utility-Libraries,
  Vulkan-ValidationLayers at 1.4.363, and SPIRV-Headers/SPIRV-Tools at the Vulkan-ValidationLayers known-good pins.
- DirectXShaderCompiler is vendored at `v1.10.2605.37` with its in-tree LLVM/Clang sources. Its test,
  unittest, example, and docs trees are not vendored, except the three `LLVMBuild.txt` files (`docs/`, `examples/`,
  `projects/`) that the root `LLVMBuild.txt` makes `llvm-build` read at configure time. Its own gitlinks name different
  SPIRV-Headers/SPIRV-Tools revisions; DXC uses the shared roots through `DXC_SPIRV_HEADERS_DIR` and `DXC_SPIRV_TOOLS_DIR`.
- SPIRV-Tools is vendored with the `tools/`, `examples/`, and `test/CMakeLists.txt` entry points that its
  top-level CMake adds unconditionally, plus `CHANGES` and all of `utils/`: `source/CMakeLists.txt` reads `CHANGES` and
  `utils/update_build_version.py`, and its generators read the `utils/generate_*.py` scripts at build time.
  Configure with `SPIRV_SKIP_EXECUTABLES=ON`, which also skips tests.
- FidelityFX FSR 2 is vendored as its `src/ffx-fsr2-api` source tree. Prebuilt binaries under `tools/sc` are
  excluded.
- Roboto (Regular, hinted) is the licensed Cyrillic-capable font.

### Build constraints for later stories

- DXC (US-003): see [Shader toolchain](#shader-toolchain). `projects/dxilconv` is not vendored.
- Vulkan-ValidationLayers: configure with `USE_MIMALLOC=OFF` (mimalloc is optional and not vendored) and tests off.
  Keep `VVL_ENABLE_TRACY=OFF`: its Tracy path is the only `FetchContent` in the vendored Vulkan trees. It needs the
  system Python 3 for its generators.
- DXC's `compiler-rt` ExternalProject is gated on `projects/compiler-rt` existing, which is not vendored, so it stays off.
- Vulkan-Loader: its generators under `scripts/` run with the system Python 3.
- Assimp: keep `ASSIMP_BUILD_USD_IMPORTER` off. `third_party/assimp/code/CMakeLists.txt` has an optional `FetchContent`
  path for Assimp's USD importer, and vendored sources must not configure it.
